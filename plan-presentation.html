THE ONE IDEA

Spec-driven design

Of everything you sent me, this is the only piece that changes what you do on Monday. Tuomas Härkönen at Futurice, August 2026. His argument:

Agents can turn clear intent into working code. So writing clear intent is the bottleneck now — and that is a designer's job.

Paraphrased from "Faster prototypes miss the point"

So the deliverable moves. Not the mockup. The spec: a plain text file, kept with the code, saying what to build, why, how you would know it worked, and what you deliberately rejected.

He also names the trap precisely — mockups show the happy path and hide the edge cases, the error states and the data rules. That is the gap the design engineer walked into on your project. Not better pixels. A fuller answer.

What he says designers keep

Discovery and research. Framing the problem. Owning the open questions. Judging meaning, ethics and usability.

What moves to agents

Pixel conformance. Token conformance. Checking the build matches the standards.

Honest note on the source: it is a consultancy blog post, and he admits his evidence is thin — "my early tests are showing promising gains," with no numbers. The idea is solid and matches the survey data. Treat his claimed results as unproven.

YOUR BIGGEST GAP

Design systems in code, in one slide

You asked

"I need to know more about how design systems connect with code, I feel I don't know much about that. What are the basics that I need to know?"

There are only five moving parts, and you already understand the first one better than most engineers do.

PartWhat it isIn plain words
1. TokensA JSON file of your decisionsYour palette, spacing, type scale and radii, written as data instead of as a Figma style. color.text.primary, space.4.
2. The buildStyle DictionaryA small program that reads your token file and spits out CSS, iOS and Android versions. You configure it once; you don't write it.
3. ComponentsCode that consumes tokensA button whose colour is var(--color-text-primary), never #16201C. That's the whole discipline.
4. The showroomStorybookA web page listing every component in every state, so people can see and test them without opening the app.
5. The deliveryAn npm packageThe system gets a version number and products install it. A change you make can be released, or held back.

Design tool → token file → build step → CSS → components in Storybook → versioned package.

That's it. That is the pipeline every design system you admire is running. You own step 1 and step 3's rules. Week 3 and week 4 of this plan are exactly those two.

Read Martin Fowler's article below — it is free, it is the clearest thing written on this, and it is written for people who are not already fluent.

Using it next week

      THE WEEK THAT MATTERS

      Week 4: make the agent obey you

      You write AGENTS.md — the rules an agent must follow in your repo. Then you ask Claude to build a screen.

      If it invents a colour, the system failed. Not Claude.

      Dean's guidance, which is a design brief in disguise

      Delegative UX is what lets a person see, track and understand work being done in their name, by an agent.

      Marie-Claire Dean, 24 Sep 2026
      • Show what the agent is doing now, and where.
      • Explain why it chose what it chose, what it assumed, what it decided against.
      • Be generous with visibility at first — "the work, the reasoning and the near-misses" — then reduce it as trust builds, task by task.
      • Design for the people affected by an agent's actions who didn't delegate it.
      • Put consequential actions behind a gate. Label each reversible or not.
